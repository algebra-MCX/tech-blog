**知识越来越多，真正稀缺的是一条足够短、足够清晰，又不牺牲深度的学习路径。**

LLM 领域变化太快，容易学得零散，不清楚掌握了什么、下一步该做什么。更要警惕把核心思考交给 Coding Agent。

张一鸣说过，你的核心竞争力是你的认知，总要有人为你的认知买单。而认知的深度不等于技术学得多，它来自你是否知道这一行最重要的问题是什么，以及你自己独有的思考是什么。这就是我建这个博客的初衷。

## 01. 尽可能快地入门

入门越快越好，但基础不能薄。我认为第一轮入门最迟不超过一周，要短时间、高强度地学，检验标准只有一个：你能不能从白板开始，重新推导核心原理。

比如学 LLM Infra，不必先花两个月学完 PyTorch。先掌握 Tensor、Autograd、GPU Execution 这些必要概念，尽快动手写一个最小推理程序，遇到问题再回头补原理。基础应该为解决问题服务，而不是变成开始之前的一道门槛。

这也是整个博客的方法论：**项目驱动学习（Project-driven Learning）**。

## 02. 每个方向，一条最短入门路线

我计划为每个主要方向建立一条精简路线，每条都配一个小项目：

- **Systems**：从最小推理引擎出发，理解 Runtime、Scheduling、GPU Kernels、分布式执行。
- **Algorithms**：从数学直觉与最小实现出发，理解模型架构为什么有效。
- **Hardware**：从 GPU 执行与存储模型入手，建立软硬件协同的直觉。
- **Agents**：从最小工具调用循环开始，理解规划、记忆、状态。
- **Data**：从可运行的数据流水线开始，理解数据系统的核心问题。

不需要一上来读几万行框架源码，先把最重要的东西做出来。

## 03. 怎样才算「出师」

我不用“看了多少篇、学了多少小时”衡量掌握程度。每个方向我会提供三样东西：**一个最小实现、几个关键实验、一组验收任务**（修改实现、解释现象、分析瓶颈）。

比如学完最小推理引擎，你应该不止会运行它，还要知道请求怎么调度、KV Cache 怎么管理、瓶颈可能在哪，以及怎么用实验验证自己的判断。做到这些，我姑且称之为「出师」。这不代表精通，而是你有了可运行的心智模型，和独立继续探索的能力。

**入门的终点，不是学完所有知识，而是具备自己继续学习的能力。**

## 04. 从局部到全局

单独学会一个 Kernel、一个 Attention 或一个 Runtime 还不够。为什么模型架构会改变推理系统的设计？为什么 GPU 的内存层次会影响算法选择？为什么有些理论上省了计算量的方法，实际反而更慢？这些问题在单一领域里找不到完整答案。

等各方向的路线完善后，我计划写一份跨领域综述，把五个方向串起来。

## 05. 代码与实验，尽可能开放

小项目、核心实验和验收任务，我会陆续在 GitHub 开源，希望它们能被运行、修改、质疑和复现。每个实验我会尽量交代版本、环境、测量方法、对照条件和已知局限。失败的实验、错误的假设和排障过程，同样值得记录。没验证的结论我会明确标注，不会把猜想写成事实。

## 06. 未来，也许可以一起研究

如果有机会，我想围绕这些项目办小规模讨论班，一起读论文、复现实验、讨论设计。不需要光鲜的背景，只要愿意动手、认真思考，并且愿意让实验结果检验自己的观点。这还只是一个设想，希望它能慢慢发生。

## 如何开始

- **刚接触某个领域**：从[最简入门](/guides/sections/quickstarts/)路线开始，完成第一个 Nano Project 和核心实验。
- **已有基础**：直接读[项目](/projects/)、源码和性能分析，不必按顺序。
- **想读些随笔**：读[「想法」](/notes/)，这里记录个人随笔与对未来的预测。

找到自己真正关心的问题，沿着它深入就好。少一点漫无目的的准备，多一点真正的动手与思考。
